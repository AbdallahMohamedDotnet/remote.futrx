# TOTP two-factor authentication, single active session, device history, and recovery-code alerting

**Status:** done
**Tier:** structural — introduces a new module boundary (session registry + 2FA authenticator), changes the session model from fully stateless to conditionally server-tracked, adds a new frontend dependency, and changes the login HTTP contract (two-step challenge). Per the `plan` skill, a structural tier requires a check-in with the user before implementation starts. That check-in happened in a live turn: the plan's one `BLOCKING` question (whether single-session/history/alert are bundled under the 2FA toggle or scoped independently) was answered — **each of the four features is independently togglable per account**, not bundled under one 2FA switch (see Risks & open questions and Approach for the resulting design). Implementation may proceed.
**Scope:** Let a user independently opt into, from Settings → Security: (1) TOTP-based 2FA (authenticator app + one-time recovery codes), (2) single active session (a new login invalidates the previous one), (3) a bounded sign-in/device history, and (4) an in-app alert when a sign-in used a recovery code instead of the normal TOTP code. (4) is necessarily a sub-setting of (1) — recovery codes only exist once 2FA is enabled — but (2) and (3) are independent of 2FA and of each other. Each toggle defaults to off; a user may, for example, turn on single active session without ever enabling 2FA. Zero behavior change for any account that leaves all four off (today's default for every account).
**Out of scope:**
- SMS/email/push 2FA methods — TOTP-via-authenticator-app and its recovery codes only, per the request ("only if from authenticator application").
- A global admin kill switch for the whole feature — it is already opt-in per account, defaulting to off, which satisfies "make it disabled." An admin can still force-reset a compromised user's 2FA (Step 9).
- Revoking already-open WebSocket connections when a session is superseded (see Risks — existing sockets have no per-message re-auth today; this plan does not add one).
- A global toast/notification system — the alert is surfaced through the existing `/auth/me` status payload and a new Security settings tab, reusing infrastructure that already exists instead of building a new one.
- Password reset flow, email-based notifications — no mail/notification integration exists in this codebase (confirmed by search); building one is a separate feature.

## Context

**Today's login/session flow**, read end to end:

- Sessions are stateless HMAC-SHA256 tokens `{email, sub, iat, exp}` (`backend/internal/service/auth/model.go:41-46`), signed/verified by `SessionCodec` (`backend/internal/service/auth/session_codec.go:17-64`) with a hardcoded 30-day expiry (`session_codec.go:13`) and no server-side store.
- `Service.CurrentSession` (`backend/internal/service/auth/service.go:150-165`) is the **single choke point** every caller uses to turn a cookie into an authenticated principal: `PrincipalResolver.Session` (`backend/internal/transport/http/principal.go:22-27`), `AccessVerifier.Verify` (`backend/internal/service/auth/access.go:31-33`), `middleware.Auth.Wrap` (`backend/internal/transport/http/middleware/auth.go:49`), `accessGate.CallerAndAdmin` (`backend/internal/transport/transport.go:163`), and the skills catalog (`backend/internal/service/skills/catalog.go:24-27, 63`). It already contains one **account-level invalidation rule** beyond pure signature/expiry checking — "once the local administrator exists, invalidate any older Google-backed sessions for that email" (`service.go:158-163`). This is the exact prior art this plan's single-session check extends.
- Login completion is currently split between the service (verify credentials, return a `User`) and the handler (mint + set the cookie): `auth_local_handler.go:62-64, 90-93` and `auth_google_login_handler.go:94` all call the shared `setSessionCookie(w, auth, user)` helper (`auth_cookie.go:9-15`), which calls `auth.SignSession(user)` (`service.go:146-148`) itself. Nothing captures IP or User-Agent at login today.
- The existing IP-based brute-force limiter (`localLoginLimiter`, `auth_local_handler.go:96-139`) is reused as-is for the new 2FA-verify endpoint rather than rebuilt.
- `/auth/*` paths are already exempt from the session-required gate in `middleware.Auth.Wrap` (`middleware/auth.go:44-47`), which is exactly what the new pending-2FA-challenge endpoint needs (it must be reachable before a full session exists).
- Per-user file stores follow one settled shape: a `New(dataDir)` constructor, a sha256-hex-of-identity filename, JSON `Get`/`Save`, temp-file+rename — see `fileusersettings/store.go:25-31, 105-112` and `fileprojectaccess/store.go:37-44, 91-127`. This is the shape the two new stores in this plan follow.
- `LocalAdminAuthenticator` (`local_admin_authenticator.go:16-32, 129-181`) is the reference for "own one piece of account state behind a mutex, cached in memory, refreshed on writes" — the shape `SessionRegistry` and `TwoFactorAuthenticator` follow.
- `Service` composes independent per-concern authenticators as private fields and exposes a flat public API (`local *LocalAdminAuthenticator`, `google *GoogleAuthenticator`, `service.go:34-41`) — the shape a new `twoFactor *TwoFactorAuthenticator` and `sessions *SessionRegistry`(distinct from the existing `sessions *SessionCodec` field — will rename one, see Steps) follow.
- Frontend: `useAuth()` (`frontend/src/state/hooks/auth/useAuth.ts`) fetches `/auth/me` once on mount and exposes `refresh()`; `AuthContext` (`frontend/src/state/context/AuthContext.tsx:22-33`) composes it with per-provider auth hooks and derives `gateOpen`. `useLocalAuthController` (`frontend/src/state/hooks/auth/useLocalAuthController.ts`) owns all local-login flow state (email/password/error/submitting) and is the pattern the new 2FA-challenge step extends rather than replaces. `SettingsPage.tsx:17-55, 238-253` defines the tab list and per-tab rendering — the pattern a new `"security"` tab follows. `requestJson` (`frontend/src/api/apiRequest.ts:11-14`) already treats any 401 as "reload the page," which is exactly the behavior a superseded session needs — **no frontend change is required** for a signed-out-elsewhere device to notice; it already reloads to the login screen on its next request.

**Reference implementation:** `backend/internal/service/auth/local_admin_authenticator.go` + its composition into `backend/internal/service/auth/service.go` — a self-contained, mutex-guarded, in-memory-cached sub-authenticator with its own store port, composed as a private field of `Service` and exposed through a handful of public passthrough methods. `TwoFactorAuthenticator` and `SessionRegistry` are new siblings built the same way. On the frontend, `frontend/src/state/hooks/auth/useLocalAuthController.ts` + `frontend/src/ui/auth/LoginScreen.tsx` is the reference the 2FA challenge step extends.

**Flow today:** `POST /auth/local/login` → `Service.LoginLocal` (credential check only) → handler calls `setSessionCookie` (which calls `SignSession`) → `Service.Status` → JSON response. Google is the same shape via `LoginGoogle`/callback. No IP/UA capture, no server-side session record, no second factor.

**Deviations:**
- The TOTP secret is stored in plaintext (base32) in the new `filetwofactor` store, not encrypted. **Why unavoidable:** the server must recompute HMAC-based codes from the raw secret on every verification; it cannot be one-way-hashed like a password. **Cost:** a `DATA_DIR` compromise now also yields every enrolled user's TOTP seed (in addition to everything else already exposed by such a compromise per `docs/known-limitations.md:17`). **Reconciliation:** consistent with, not worse than, the project's existing plaintext-secrets posture (`session.key`, `oauth.json`, project secrets are all already plaintext at 0600); no new encryption-at-rest mechanism exists to reuse, and building one is out of scope for this feature. Recorded here rather than silently accepted.
- Recovery codes are hashed with SHA-256 (not argon2id like passwords). **Why:** recovery codes are generated with ~60 bits of server-chosen entropy (unlike human passwords), so a slow KDF adds cost without adding real resistance, and a login may need to check a candidate code against up to 10 stored hashes — doing that 10x with argon2's 19 MiB/iteration cost is disproportionate. **Cost:** marginally weaker if the hash file itself leaks and codes are guessed offline — but a 60-bit-entropy code is not brute-forceable offline regardless of hash speed. **Reconciliation:** documented as an intentional, narrower-scope choice; `password.go`'s argon2id path is untouched and still used for real passwords.

## Design

### Forces

- **The account holder must be able to turn 2FA on/off themselves, off by default.** Directly requested ("make this feature open make it disables"). Forces: a self-service enroll/confirm/disable flow gated only by "is this your own account," not an admin-only surface.
- **Existing accounts must see zero behavior change until they opt in.** Requested implicitly (feature must ship "disabled") and reinforced by the existing zero-lookup-per-request session model that most of the fleet depends on. Reinforced by a live follow-up decision: the four features (2FA, single-session, history, recovery-code alert) are **not a bundle** — a user can turn each on or off independently. Forces: every new check (single-session, history, alert) must be conditional on its own independent per-account flag, not on the presence of a 2FA record (except the alert, which is inherently a sub-setting of 2FA — see Approach).
- **A stateless session cannot support "one active session" or "history" on its own** — there is nothing to revoke or list without server-side state. Forces: a server-side session registry, consulted per-account only for whichever of its independent feature flags are actually on, to avoid turning every request for every account into a file-store lookup.
- **A second factor must be checked *before* a real session is issued, not after.** Forces: a distinct, short-lived, stateless "pending login" credential distinct from a real session cookie, carrying just enough claims to complete the second step without server-side pending-login storage.
- **Recovery codes must be single-use and the specific signal ("used a recovery code") must be distinguishable from normal 2FA use**, because that is the concrete, buildable reading of "alert if an imposter signs in via recovery keys" — the server cannot know intent, only which factor was presented. Forces: the sign-in method must be recorded richly enough (`password`, `google`, `password+totp`, `google+totp`, `password+recovery-code`, `google+recovery-code`) to drive the alert condition precisely.
- **QR enrollment needs a QR renderer; none exists in either the Go or JS dependency tree.** Forces a choice between a new backend dependency, a new frontend dependency, or no QR (text-only). See Patterns for the resolution.
- **A `GET /auth/me` response is already fetched by every authenticated client on load and after login**, and already only reveals account-scoped fields when authenticated. Forces reusing it as the alert-delivery channel instead of building new global-notification infrastructure that nothing else in the app has.

### Approach

Two-factor authentication, single active session, sign-in history, and recovery-code-use alerting are **four independent, per-account opt-in switches**, all surfaced on a new **Settings → Security** tab, none a prerequisite for another except where the data itself makes that unavoidable.

- **TOTP 2FA** (`twoFactorEnabled`, tracked by the existence of a `TwoFactorRecord`): the server issues a secret and a QR/manual-entry pair, the user confirms one code from their authenticator app, and the server persists the record and returns ten recovery codes (shown once). From that moment, that account's logins require a second step (`/auth/2fa/verify`) after password or Google sign-in succeeds.
- **Single active session** (`singleSessionEnabled`): independently of whether 2FA is on, flipping this switch makes the existing single choke point `Service.CurrentSession` start enforcing that only the most recently issued session ID is valid for that account, using the new server-side session registry.
- **Sign-in history** (`historyEnabled`): independently of the other two, flipping this switch makes every session issued for that account get appended (bounded, newest-first) to a per-user history file the user can see in the same Security tab.
- **Recovery-code alert** (`recoveryCodeAlertEnabled`): because a recovery code can only be *used* once 2FA is enabled, this fourth switch is only meaningful — and only shown/settable — while 2FA is on. When on, a login that completes with a recovery code instead of a normal TOTP code is recorded and surfaced as a `securityAlert` field on the already-polled `/auth/me` status, until the user acknowledges it.

The three registry-backed flags (`singleSessionEnabled`, `historyEnabled`, `recoveryCodeAlertEnabled`) live together in one `SecurityPreferences` record per account, stored alongside session history in the new `filesessions` store; `TwoFactorRecord` (in `filetwofactor`) continues to represent 2FA enrollment on its own, unrelated to the other three except as the prerequisite for the alert flag being settable. An account that leaves every flag off — today's default for every account — is byte-for-byte unaffected: no registry lookup differs from today's behavior, no history file is written, no alert field ever appears.

### SOLID review

- **S:** `TwoFactorAuthenticator` (enrollment/verification/recovery-code policy) and `SessionRegistry` (single-session + history persistence, plus the three independent `SecurityPreferences` flags that gate them) are split into two sub-components because they change for different reasons — a TOTP algorithm/format change never touches session bookkeeping, and a session-history retention-policy or preference-toggle change never touches TOTP verification. `SecurityPreferences` lives on `SessionRegistry` rather than `TwoFactorAuthenticator` because two of its three flags (`singleSessionEnabled`, `historyEnabled`) are meaningful with or without 2FA.
- **O:** Adding a future second-factor *method* (were one ever wanted) would mean adding a new verification branch in `CompleteTwoFactorChallenge` next to TOTP/recovery-code, not modifying `CurrentSession`'s single-session rule or `SessionRegistry` at all — the two are already decoupled today, this plan doesn't need to invent new abstraction for it (no `if/switch` on method exists to open — YAGNI, not built preemptively).
- **L:** N/A in the classical sense — no interface has two implementations here. The one interface pair (`TwoFactorStore`, `SessionRegistryStore`) each has exactly one implementation (`filetwofactor`, `filesessions`), matching every other store port in this codebase (`fileusersettings`, `fileprojectaccess`) — introduced for the same reason those were: to keep `service/auth` free of file-I/O detail, not because a second implementation is anticipated.
- **I:** `TwoFactorStore` and `SessionRegistryStore` are two separate, narrow interfaces (get/save one record each) rather than one fat "security store" interface — a caller needing only session history never has to satisfy TOTP-record methods it doesn't use, matching the existing narrow-port convention (`LocalAdminStore` vs `OAuthConfigStore` are already split this way inside `Store`).
- **D:** `serviceauth.Service` depends on the two new store ports as interfaces, not concrete file-store types, injected at the one composition root (`service/services.go`'s `newAuth`) — exactly how `Store`/`UserDirectory`/`OAuthProviderFactory` are already injected today (`service.go:50-57`).

### Extension points

| Extension point | Mechanism | Variation anticipated | Why plausible now |
| --- | --- | --- | --- |
| `SignInMethod` enum on session records | A closed set of string constants (`password`, `google`, `password+totp`, ...) checked by the alert condition | None speculative — this is the minimum enum needed to express the two required alert-triggering values today; not designed for hypothetical future methods | The request explicitly asks for the recovery-code-specific alert condition now, so the enum must exist now — it is not a "might add later" extension point, it is required by this plan's own scope |

No other extension points are introduced. Everything else in this design is sized exactly to the current requirement — a second TOTP-adjacent method, a global admin kill switch, and WebSocket-level revocation were all considered and explicitly placed in "Out of scope" rather than stubbed in as unused hooks.

### Maintainability

- Placement matches the existing per-concern package/file layout exactly (see Architecture conformance table); no new top-level package is introduced beyond the two file-store siblings that already have direct precedent.
- No duplicated utility: the `signedPayload[T]` extraction removes what would otherwise be three copies of HMAC sign/verify/expire logic.
- New dependency (`qrcode`, frontend only) is justified in Patterns and isolated behind a single wrapper component so it can be swapped without touching enrollment logic.
- Nothing is deleted by this change except the eventually-redundant `SignSession` method (superseded by `IssueSession`/the `Complete*Login` methods) once its three call sites and test references are migrated (Step 10).

## Risks & open questions

- [x] **Resolved (was `BLOCKING`):** should single-active-session + device history + recovery-code alerting apply only to accounts that enable 2FA, unconditionally to every account, or independently per feature? **Answered in a live turn: independently per feature.** The user can turn on 2FA, single active session, history, and the recovery-code alert as four separate switches; none but the alert (which is inherently a 2FA sub-setting, since recovery codes require 2FA) depends on another being on. This still satisfies "make this feature open, make it disabled" per-switch, and each flag is read from the same in-memory-cached `SecurityPreferences` record as the existing `twoFactor.Enabled()` gate, so the zero-per-request-file-I/O property for accounts that opt into nothing is preserved — the cost of decoupling is one extra in-memory struct-field check per authenticated request for the ~0% of accounts that opt into anything at all, not a new file lookup. Steps 5, 9, 10, and 12 were updated to reflect this before implementation started.
- Live WebSocket connections (chat, terminal, workspace) are authenticated once at handshake and never re-checked — a superseded session does not disconnect an already-open socket. → Mitigation: documented as a residual limitation (Step 19); building socket-level re-auth is a separate, larger change and is explicitly out of scope.
- Enabling 2FA mid-session must not lock the enrolling user out of their own current tab. → Mitigation: `ConfirmEnrollment`'s HTTP handler re-issues the *current* session as a tracked one in the same response (Step 12), so the enrolling browser is always the "active" session immediately after confirmation.
- Losing both the authenticator device and all recovery codes leaves an account permanently 2FA-locked (no password-reset flow exists to fall back on). → Mitigation: an admin can force-disable a member's 2FA the same way admin user-management already works today (a follow-up, not built by this plan, since no such "reset" affordance exists yet for *any* account attribute — noted as a fast follow, not blocking, since the local admin already has direct filesystem access to delete the offending `DATA_DIR/twofactor/<hash>.json` file as an escape hatch, mirroring the existing documented recovery path "recovering a lost owner password requires manually deleting `local-admin.json`" in `docs/known-limitations.md:43`).
- The new `qrcode` frontend dependency needs an actual security/maintenance check (license, last-publish date, transitive deps) before `npm install` is run — not yet vetted in this planning pass. → Mitigation: vet at implementation time before adding to `package.json`; if it fails vetting, fall back to text-only enrollment (secret + otpauth URI, no QR) as already scoped as an acceptable (if worse) alternative in Patterns.

- Initial draft treated "single session" and "history" as unconditionally global without surfacing that as a real fork in the design — fixed by promoting it to the one `BLOCKING` open question rather than silently deciding it, per the tier's required check-in.
- Remaining item a cold reader would still ask: "what exact npm package name is `qrcode`, and has it been vetted?" — intentionally left open in Risks rather than guessed, since dependency vetting is implementation-time work this plan should not fabricate an answer for.

## Outcome

**Deviations from the plan:** (1) The plan's original design tied single-active-session/history/alert to the 2FA opt-in as one bundle and filed that as the one `BLOCKING` question. The user's live answer was a third option — independent per-feature toggles — which changed the design (a `SecurityPreferences` struct with three independent bools, not gated on `twoFactor.Enabled`) before any code was written; the plan document itself was updated first (Approach, Patterns, SOLID review, Steps 5/9/10/12/16, Risks, Verification plan) to record this, then implementation followed the corrected design throughout. (2) Found and fixed one additional `serviceauth.New`/`newAuth` call site the plan didn't enumerate (`backend/internal/service/services_test.go`'s `TestNewAuthAllowsLocalAdminWithoutGoogleOAuth`) — absorbed as anchor drift, not a design change. (3) `qrcode`'s dependency vetting (flagged as an open risk in the plan) passed, so the QR-rendering path was implemented as designed rather than falling back to the text-only alternative the plan had scoped as acceptable.

**Plan defects:** None beyond the one `BLOCKING` question and the one missed call site above, both resolved during implementation. The plan's step-by-step sequencing (extract `signedPayload` → add `SID` → TOTP → recovery codes → models/ports → stores → wire composition → sub-components → extend `Service` → handlers → retire `SignSession` → frontend) held up exactly as written and each step's own `Verify:` was runnable without modification.

**Steps not fully verified:** None. All 20 steps carry a `verified` (or `verified-indirectly`, for Step 18, which had nothing to register) status with a note of what was actually observed.

**Left behind:** (1) No admin-facing "force-disable a member's 2FA" affordance exists yet — documented in `docs/known-limitations.md` as a known gap with the same manual-file-deletion escape hatch the plan scoped as acceptable (not blocking, per the plan's own Risks section). (2) WebSocket connections opened before a session is superseded remain live until they naturally close — documented as an explicit residual limitation in `docs/known-limitations.md`/`docs/threat-model.md`, per the plan's Out-of-scope section. (3) The pre-existing `npm audit` findings in `nanoid`/`postcss`/`vite` (unrelated to the new `qrcode` dependency) were left untouched — out of scope for this plan.

**For the next plan in this area:** The `CurrentSession` choke point and `SessionRegistry`/`TwoFactorAuthenticator` sub-component split held up well for adding account-scoped, opt-in behavior without touching any of the ~6 existing call sites' logic — only their call signature (adding `ctx`). If a future plan wants to add a fifth independent security toggle, the `SecurityPreferences` struct and its handler (`/api/me/security/preferences`, partial-update-by-pointer-fields) is the natural extension point; no new architecture should be needed. If a future plan needs admin-facing account-recovery affordances (force-disable 2FA, force-logout a member), that is genuinely new surface — no such "reset another account's security state" pattern exists anywhere in the codebase today, so it will need its own authorization-policy design, not just a passthrough method.
